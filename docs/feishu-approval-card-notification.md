# 飞书卡片与供应商报价通知

## 当前版本

当前审批/业务通知卡片版本为 `v20260812.2`，供应商报价通知卡片版本为 `v20260812.1`，系统版本为 `v20260812.2`。只要修改卡片结构、按钮行为或字段含义，都要同步递增对应卡片与系统版本。

供应商在“已售管理”上传发票或送货单并成功提交事务后，系统复用业务通知卡向来源申请对应的部门助理发送提醒。通知包含订单号、申请单号、供应商、资料类型、版本、上传人和文件数量，并引导助理进入“采购管理 / 我的订单”核对或补传另一类资料。助理或最高管理员自行补传时不发送该提醒，避免重复通知。

- `FeishuApprovalCardServiceImpl.CARD_TEMPLATE_VERSION`
- `FeishuBotServiceImpl.BOT_CARD_VERSION`
- `SupplierFeishuNotificationServiceImpl.CARD_VERSION`
- 前端 `systemUpdates.ts` 的首条版本（`AppLayout.vue` 自动读取）

旧飞书消息不会自动变成新版本，需要在“飞书卡片日志”或“供应商报价卡片日志”里重新发送。

## 审批卡片

系统通过本地心跳扫描 `approval_task` 待审批任务，向审批人发送飞书交互卡片。普通节点可在卡片里同意全部、退回整单，也可在楼长及后续节点对明细做单项驳回。

审批卡片基础信息区显示“需求提交人”。普通采购读取当前申请的 `applicant_user_id`；月度汇总采购按每条明细的 `source_request_id` 回查源申请人，不使用汇总触发人、当前审批人或管理员抄送人代替。只有一名需求人时显示姓名；多人汇总时显示姓名摘要，并在每条采购明细和替换商品明细中标注对应需求提交人。历史申请缺少明细来源时回退到当前申请人。

系统选出中标商品后，仅按已中标商品比较中标单价和参考单价。高于参考价 13% 的商品进入“楼长超价复核”，截止时间为任务创建后 24 小时。卡片展示提交者、来源工单、中标供应商、参考价、中标价、超出金额和比例；楼长只能通过或单项驳回，不能退回整单。单项驳回后仅该商品停止采购，同一申请的其他商品继续流转。通过商品必须填写具体价格合理原因。系统在剩余 12 小时、2 小时及逾期时发送提醒，逾期不会自动通过。

审批卡片复用原系统审批流程，不新增独立审批节点。整单退回使用现有 `RETURN` 动作；单项驳回复用线上审批的 `itemDecisions`，本质上是流程继续流转，同时把指定明细标记为驳回。

卡片使用飞书 JSON 2.0。底部同意、退回、系统处理按钮横排展示。单项驳回区域支持多选，点击明细右侧“驳回本项”只做临时标记，明细保留并显示删除线，按钮变为“恢复”；填写原因后点击“提交单项驳回”才真正提交。

“系统处理”按钮优先读取平台集成设置中的 `feishu_approval_card_system_action_url`，默认打开登录后跳转工作台的完整地址；如果未配置该入口，则回退到 `feishu_approval_card_app_base_url` + 审批路径。`feishu_approval_card_app_base_url` 仍作为系统访问基址和 AI 图片中转兜底使用，不要直接填成带 `/login?redirect=...` 的页面链接。

采购明细每页展示 10 条，超过 10 条通过“上一页 / 下一页”在卡片内翻页。采购明细中的电商链接在卡片正文显示为“打开商品”链接；单项驳回确认弹窗只展示被驳回的商品明细，不展示系统 URL 或商品 URL。

采购明细存在单价、数量或金额小于等于 0 时，卡片会展示金额校验提示并禁用“同意全部”。后端审批接口也会再次校验，避免旧卡片绕过 0 元限制。

报价定标后，如果中标明细包含供应商替换商品，审批卡片会切换为“替换商品待确认”专用卡。卡片只展示前 10 条替换商品，说明原商品、替换商品、供应商、替换报价和原因，并显示固定资产/低值易耗分类；二手商品单价达到 1000 元时另行标记“需特殊审批”。点击“同意替换”后后续审批金额和订单明细按替换商品执行，点击“不同意替换”或 2 天内未确认时按原商品继续。统一工作台支持在每个中标替换组内独立选择原商品报价或替换商品报价，当前交互为直接点选每组里的原商品/替换商品卡片，不再显示下方二次选择栏；替换商品报价块会显示提出替换报价的供应商名称和联系方式；待处理节点不预选，必须手工选完每组后提交，并通过 `replacementDecisions` 写回每条中标报价。该确认仍调用原 `WorkflowService` 和 `NODE_APPLICANT_REPLACEMENT_REVIEW`，不新增旁路流程。

## AI 审核意见

AI 助手生成的采购申请会把 `AI审核意见` 写入 `purchase_request.ai_review_opinion` 独立字段，不写入业务备注。意见必须以“建议通过：”“建议补充：”或“建议退回：”开头，便于审批人先看结论。

正式审批卡、已处理卡和申请人结果通知都会展示同一条 AI 审核意见。历史数据如果该字段为空，卡片会按申请 ID 回查 `procurement_ai_session.ai_summary` 兼容展示。

## 供应商报价卡片

供应商报价任务卡片不跳转内网页面。点击“下载询价单”后，后端生成 Excel 询价单，上传到飞书，并把文件消息发送到当前单聊或外部群。卡片必须展示“报价截止”和“报价类型”；报价截止按延期/3 小时倒计时优先，否则按报价开启时间加 `quote_open_days` 计算；报价类型需同时写明公开询价/定向报价和总价最低/分项最低中标规则。

新版询价单必须包含以下信息：

- 业务可见字段：行号、物料编码、商品名称、规格型号、电商链接、收货城市、数量、单位、需求日期、采购原因。
- 供应商填写字段：是否替换商品、替换商品名称、替换规格型号、替换商品链接、替换商品单价、替换原因、是否放弃报价、报价单价、交期天数、报价备注、报价说明。
- 系统匹配字段：申请单号、采购申请 ID、采购明细 ID、供应商 ID、供应商编码。

`电商链接` 是供应商报价的重要参考字段，导出的询价单必须从 `purchase_request_item.ecommerce_url` 写入该列。已有旧版本文件不会自动补链接，需要重新点击“下载询价单”生成新版文件。

如供应商填写“是否替换商品=是”，必须同时填写替换商品名称和大于 0 的替换商品单价；替换报价进入原供应商报价流程，中标后再由采购申请人确认是否采用。

供应商填写报价后，直接把同一个 `.xlsx` 或 `.xls` 文件发回机器人。机器人收到 Excel 文件消息时，必须先尝试按 `supplier_feishu_binding` 识别供应商并下载附件，再考虑内部系统用户绑定；否则外部供应商会被误判为“系统账号未绑定”。

导入成功后，后端调用现有 `SupplierQuoteService.submitQuote`，继续走原“供应商报价、比价、中标确认”流程，不新建旁路流程。导入日志类型为 `SUPPLIER_QUOTE_FILE_IMPORT`。

供应商中标确认卡片点击“确认中标”后，会自动以供应商身份调用原 `SupplierQuoteService.exportAward`，生成中标清单 Excel 并发送到当前单聊或外部群；已处理卡片仍保留“下载中标清单”按钮用于重试。未确认中标时即使旧卡片触发下载动作，后端也会拒绝。

## 外部供应商绑定

采购管理员先在系统“供应商管理”里维护并启用供应商。供应商拿到供应商编码后，在机器人单聊或外部群发送：

```text
绑定 SUP0001
```

系统会把当前单聊或外部群写入 `supplier_feishu_binding`。后续报价任务会推送到该会话；如果供应商只发送“我要绑定”等没有编码的消息，机器人返回绑定引导，不再提示内部账号未绑定。

供应商本人收卡需要满足两个条件：后台启用供应商报价通知，并且存在有效供应商飞书绑定。管理员抄送卡片只依赖管理员账号可解析出邮箱或飞书 ID，不要求供应商已绑定。

## 飞书权限

企业自建应用至少需要：

- 机器人能力已启用，并发布到企业。
- 发送消息权限，用于发送审批卡片、供应商报价卡片和文件消息。
- 上传文件权限，用于生成并上传询价单 Excel。
- 下载消息资源权限，用于供应商把 Excel 发回机器人后，后端下载附件。
- 长连接事件订阅已启用，并订阅 `card.action.trigger` 和消息接收事件。
- 如使用组织同步，还需要通讯录读取权限，并确保应用可用范围覆盖目标部门。

如果供应商文件能发到聊天里但系统没有导入，优先检查消息接收事件、下载消息资源权限、机器人可用范围和 `supplier_feishu_binding`。

## 常见排查

- 看到“账号未绑定系统用户”：内部员工先检查用户管理里的邮箱、手机号或飞书 ID；外部供应商先发送 `绑定 供应商编码`。
- 询价单缺少电商链接：说明下载的是旧版本文件，重新点击新版“下载询价单”。
- 供应商回传 Excel 后仍提示未绑定：确认该聊天或发送人已经写入 `supplier_feishu_binding`，并检查后端是否先执行供应商附件导入分流。
- 点击卡片报 `200673`：通常是卡片 JSON 结构或按钮 value 写入了飞书不接受的空值，检查回调日志和卡片版本。
- 飞书文件下载失败：检查消息资源下载权限、tenant access token、message_id 和 file_key 是否完整。
