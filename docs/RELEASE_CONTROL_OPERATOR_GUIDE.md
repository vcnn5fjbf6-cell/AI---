# 上线管理操作说明

“平台管理 / 上线管理”用于把已经完成开发和 PR 构建检查的更新组合成一个发布批次，先部署到 151 测试环境验收，再由上线管理员确认发布生产。

## 使用条件

- 仅平台超级管理员可以打开上线管理。
- 更新必须提交为面向 `main` 的非草稿 PR，且不存在合并冲突。
- PR 的前后端构建必须通过，并且检查结果仍对应当前 `main`。
- 修改发布流水线、Runner 门禁、测试部署脚本或生产编排的 PR 不允许从页面自动上线，必须单独人工审核合并。
- 上线管理账号与平台登录账号分开，由运维人员单独发放；操作说明不保存账号密码或发布凭据。

## 标准上线流程

1. 打开“平台管理 / 上线管理”，在“可上线更新”中查看 PR 标题、模块标签、改动文件和拦截原因。
2. 如只上线某个业务板块，先点击模块筛选标签，例如“采购管理”“维保管理”“灾害预警”或“平台管理”，再点击“选择当前模块可上线项”。
3. 勾选一个或多个状态为“可选择”的更新，点击“创建上线批次”。同一时间只允许存在一个活动批次。
4. 系统自动组合所选更新，构建固定版本的前后端镜像，并先使用一次性干净数据库完成启动和增量脚本验证。
5. 干净数据库验证通过后，系统把同一版本部署到 151 共享测试站。业务人员在测试站检查登录、页面、接口和本次改动。
6. 批次显示“待确认上线”后，再核对批次中的更新、测试版本、涉及模块和操作人。只有当前测试站仍运行该批次时，页面才允许确认生产。
7. 点击“确认上线”后，生产只拉取测试阶段确认过的程序版本。页面持续显示生产进度，成功后批次进入“已上线”并保留 Actions 链接。

## 模块化上线

上线管理会根据 PR 的变更文件自动识别模块，并把模块标签展示在候选更新和历史批次中。当前模块标签包括：

| 模块标签 | 典型范围 |
| --- | --- |
| 工作台 | 统一请求队列、工作台公告和工作台接口 |
| 采购管理 | 采购申请、月度需求、报价、订单、售后、个人劳保和采购 AI |
| 供应商 | 供应商账号、报价入口和供应商侧页面 |
| 维保管理 | 维保记录、维保流程和维保页面 |
| 灾害预警 | 天气预警、湿球温度、飞书预警卡片和预警设置 |
| 平台管理 | 用户、角色、权限、部门、平台集成、系统更新和后台管理页面 |
| 数据库脚本 | Flyway 脚本、生产幂等 SQL 和结构脚本 |
| 发布基础设施 | GitHub/Gitee workflow、部署脚本、Runner 门禁、Compose 和上线控制面 |
| 文档说明 | README、操作手册、PRD 和使用说明 |

模块筛选只负责帮助选择更新，不改变发布安全门：被选择的 PR 仍必须通过当前主线上的 PR 构建检查；创建批次后仍会重新部署到测试环境做组合验收；生产仍需要上线管理员输入确认词。涉及“发布基础设施”的 PR 仍然会被拦截，不能通过普通业务批次自动上线，必须单独人工审核后部署控制面。

## 批次状态

| 页面状态 | 含义 | 处理方式 |
| --- | --- | --- |
| 准备中 | 正在组合所选更新 | 等待系统完成，不重复创建 |
| 测试中 | 正在构建并部署 151 | 通过批次链接查看进度 |
| 待确认上线 | 测试部署成功，等待人工确认 | 完成业务验收后确认生产 |
| 已上线 | 生产部署和健康检查成功 | 无需继续操作 |
| 测试失败 | 构建、数据库或测试部署未通过 | 查看失败记录，修复后重新创建批次 |
| 已过期 | `main` 或测试站已发生变化 | 刷新候选并重新创建批次 |
| 生产失败 | 生产任务未完成 | 先确认生产现状；满足页面安全条件时使用“重试” |

## 常见拦截原因

- **未找到与当前主线匹配的 PR 构建检查**：PR 创建时间较早或 `main` 已更新，需要把 PR 同步到最新主线后重新运行检查。
- **PR 存在冲突或尚未完成可合并性检查**：先在 PR 中解决冲突，等待 GitHub 完成可合并性计算。
- **涉及受保护的发布基础设施**：该 PR 不能进入自动批次，需按基础设施变更流程人工审核。
- **当前已有活动发布批次**：先完成或处理现有批次，避免两个版本同时修改测试站或生产。
- **测试环境当前版本已变化**：151 已被后续测试部署替换，原批次不能继续确认生产，需要重新创建并验收。

## 操作边界

- 页面不会因为 PR 合并或 `main` 更新自动发布生产。
- 不允许跳过测试、直接填写提交号或替换测试通过的镜像。
- 不在页面、业务数据库、PR 或文档中填写 GitHub 私钥、Token、HMAC 或服务器密码。
- 每次创建、确认和重试都会记录批次、操作账号、时间、提交版本和流水线链接，作为发布审计依据。

## 上线管理员密码恢复

当独立上线控制台持续返回 Basic 登录框、已确认用户名无误且原密码无法通过时，按以下受控流程恢复：

1. 由仓库管理员创建一次性仓库 Secret `RELEASE_ADMIN_PASSWORD_RESET`，值必须为不少于 32 个字符的随机密码。
2. 在 GitHub Actions 手工运行 `Deploy Trusted Release Control`，勾选 `reset_admin_password`。
3. 流水线只在受信任的 151 Runner 上原子更新宿主机 `.env`，重新构建控制面并完成健康检查；密码不会进入参数、日志、状态文件或镜像。
4. 使用新密码验证控制台登录成功后，立即删除仓库 Secret `RELEASE_ADMIN_PASSWORD_RESET`。正常部署不会读取或修改宿主机密码。

该流程只恢复上线控制台账号，不修改平台用户、业务数据库、GitHub App、生产 HMAC 或测试/生产应用配置。
